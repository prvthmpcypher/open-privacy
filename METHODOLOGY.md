# Methodology

**Open Privacy** · v0.1 · July 2026 · Poorvith M P

## Selection rules

1. **One primary tool** per category — best everyday default for a privacy-curious user.
2. Prefer **open source** when quality and multi-platform support are comparable.
3. Cross-check public privacy catalogs (e.g. pluja/awesome-privacy, Privacy Guides, AlternativeTo) and vendor install pages before locking a pick.
4. Do **not** recommend abandoned projects as primary.
5. Proprietary tools are allowed when FOSS options fail a hard practical catch; label honestly.
6. **Catch alternatives:** exactly one alternative per concrete catch (OS gap, payment, region, skill, product surface).
7. **Local open-source path:** always name a local/self-hosted FOSS option when one exists; otherwise mark N/A.
8. **Install steps:** copy actionable steps from the tool’s official install documentation; do not invent commands.
9. **v0.1 excludes** threat-model essays and per-OS “source citation” lines on category pages.
10. No affiliate links. State limitations clearly.

## India-usable notes

When a catch is payment, KYC, or regional availability, prefer documenting a practical alternative that still works for users in India when possible.
