# Methodology

**Open Privacy** · v0.2 · August 2026 · Poorvith M P

## Selection rules

1. **One primary tool** per category — best everyday default for a privacy-curious user that balances strong encryption, active maintenance, and multi-platform convenience.
2. Prefer **open source** when quality, security audits, and multi-platform support are comparable.
3. Cross-check public privacy catalogs (e.g. `pluja/awesome-privacy`, `Privacy Guides`, `AlternativeTo`) and vendor install pages before locking a pick.
4. Do **not** recommend abandoned or unmaintained projects as primary.
5. Proprietary tools are allowed only when FOSS options fail a hard practical catch (such as hardware-specific mobile limits or banking compatibility); label honestly.
6. **Catch alternatives:** exactly one alternative per concrete catch (OS gap, payment, region, skill, product surface).
7. **Local open-source path:** always name a local/self-hosted FOSS option when one exists; otherwise mark N/A.
8. **Install steps:** copy actionable steps from the tool’s official install documentation; do not invent custom scripts.
9. **No affiliate links or sponsored placements.** State limitations clearly.
10. **Official Assets Only:** All logos must be downloaded directly from upstream projects or simple-icons; never AI-generated.

## India-usable notes

When a catch is payment, KYC, or regional availability, prefer documenting a practical alternative that works for users in India (such as UPI/cash hygiene or non-US-exclusive tools) when possible.
